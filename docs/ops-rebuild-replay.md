# 重算开市前走势（运营）

开市前（线上是 2026-07-01 到开市前一天）的 K 线和营收不是真实交易，是开服时 `server/seed.py` 用当时的模型回放出来的（K 线标记为 `source='replay'`）。模型升级后（例如 v0.6.0 的长尾收入、`demand_base_week` 250 万 → 162 万），这段历史和开市后的走势不再一致，K 线在开市日有断层。`server/tools/rebuild_replay.py` 用当前模型重新回放这段时间，替换这部分历史。以后每次模型升级后都可以再做一次。

## 它改什么、不改什么

只改开市前的历史：

- 每支有回放历史的股票：`source='replay'` 的 K 线；开市日之前的 `company_days`（营收、各市场营收、已播集数、每股分红）；`companies.ipo_price`（发行价）。
- 新走势整体按比例缩放，使最后一根回放 K 线的收盘价等于原来的值。这个值就是开市参考价，也是开市第一天的昨收，所以 K 线在开市处没有缺口；发行价按同一比例缩放。营收和分红是模型的原值，不缩放。
- 回放从数据窗口第一天的开服状态开始（同一个 `server.seed`，只回放到第一天）。窗口第一天已经在播的作品不从开播前的先验起步：工具先按同样的规则生成窗口之前 120 天的每日输入（与服务器重建估值时读的天数相同），估值依次走过这些天，得到窗口第一天“当时可知”的状态。开盘价设为这个估值，然后每天用当天的每日输入文件（`data/derived/inputs/<日期>.json`）做日结、由 NPC 市场交易。某一天只读那一天的文件，后来才有的数据不会出现在更早的日子里。回放期间不发生拆股、配股、回购（开市前没有这些操作）。

不改：账号、资金、持仓、成本、委托、成交、账本、估值状态（`valuation_joint`）、新闻、宏观数据，以及开市日及以后的所有 K 线和营收。工具在同一个事务里写入前后各算一次这些数据的摘要，有任何不同就整体回滚。

新回放没有走到开市前一天的股票（新回放里还没上市、已退市或并入别的公司）保留原来的历史，在报告末尾列出（`kept as is`）。

对开市后的影响：

- 日结判断退市时看最近 7 天的营收，个股页的“近 4 周每股收益”“近 4 周每股分红”“股息率”也会用到开市前几周的营收和分红。重算后，开市后最初几周的这些数字按新历史计算。原来的回放没有分红记录，重算后有（模型按当时营收发放的每股分红，不随价格缩放）。
- 开市后、升级到新模型之前由旧版本日结的那几天，营收仍是旧模型的规模（例如 v0.5.x 的需求规模是 v0.6.0 的 250/162 倍）。工具不改开市后的数据，所以营收图的台阶会从开市日移到升级日。

回放的前几周：窗口第一天（7 月 1 日）正好是夏季番开播的时候。7 月上旬新番陆续开播，美国市场的总关注度从 6 月底约 6 万升到 7 月中约 15 万，已在播作品的份额随之下降，估值也下降。在测试副本上，按市值加权，前 10 天估值下降约 33%，此后每 10 天平均下降 4%–13%。用截至 7 月 5 日的数据从头重建估值，结果与回放里 7 月 5 日的估值相差约 6%，说明这段下跌来自当时可知的数据，不是回放的起步方式造成的。

开市日以数据库状态 `launched_on` 为准（工具读取，不需要指定）。

## 前提

- 服务器上的代码和服务程序是同一版本，`bin/anistock` 支持 `replay-history` 子命令（v0.6.1 起）。
- 每日输入已经用 v0.6.1 的 `engine/daily_inputs.py` 重新生成，从数据窗口第一天到上一个已结算的交易日每天都有文件。缺任何一天，工具会报错退出，不写数据库。v0.6.1 起，作品的中国、日本数据源（`sources`）按时点判断：采集器第一次拿到对应的 Bangumi 条目或 Annict 作品的那天起才算有这个数据源。用 v0.6.0 生成的历史文件按生成时的对应表填写，后来才接入的数据源会出现在更早的日期里，所以要重新生成（服务器重建估值读的也是这些文件）：

  ```bash
  set -a; source .env; set +a
  uv run engine/daily_inputs.py --from 2026-07-01 --day <上一个已结算的交易日> --force
  ```
- 磁盘上有游戏数据库大小的空余空间（备份）。

## 步骤

避开每天 06:30 的日结。回放约需 15–20 分钟（测试副本 141 支股票、125 天用了 15 分钟），整个过程约 30 分钟，期间游戏不可用。

### 1. 停服

```bash
cd ~/anistock
systemctl --user stop anistock-server
```

服务器把公司和行情放在内存里，运行中改数据库它看不到，还可能把改动覆盖掉。工具发现有其他进程打开了数据库就会拒绝运行，并列出进程号。

### 2. 预演

```bash
set -a; source .env; set +a      # 与服务相同的环境（ANISTOCK_DB、ANISTOCK_INPUTS_DIR 等，未设置时用默认路径）
uv run python -m server.tools.rebuild_replay data/game.db --dry-run --work /tmp/rebuild-replay
```

- `--work` 保留中间文件，第 3 步用 `--history` 直接复用这次回放，不必再等一遍。
- 输出每支股票一行：第一根和最后一根回放 K 线的收盘价（原 → 新）、缩放比例、发行价（原 → 新）、回放天数、开市第一天的开盘价。
- 检查：最后一列收盘价“原”和“新”相同；缩放比例大多在 0.5–2 之间（偏离很大的股票，说明新模型对它开市前的估值差别大，记下来）；`kept as is` 的股票不多。

### 3. 执行

```bash
uv run python -m server.tools.rebuild_replay data/game.db --history /tmp/rebuild-replay/history.json
```

- 先把数据库备份到同一目录：`data/game-before-rebuild-<时间>.db`，路径会打印出来。
- 最后一行应是 `rewrote the replay history of N stocks; untouched tables verified (...)`。
- 出错时数据库保持原样（事务回滚），备份仍然保留。

不用 `--history` 也可以，工具会重新回放一遍，结果相同。

### 4. 启动

```bash
systemctl --user start anistock-server
journalctl --user -u anistock-server -n 30 --no-pager
rm -rf /tmp/rebuild-replay
```

### 5. 检查

- 个股页日 K：开市前的 K 线颜色较淡，开市处有一条细竖线；竖线两侧价格衔接，没有跳空。
- 经营栏的营收图：开市前后连续，没有台阶。
- 市场页指数、排行、持仓页的数字与停服前一致（开市后的数据没有变）。
- 第二天日结后日志没有异常。

## 恢复

停服，用第 3 步的备份替换数据库，再启动：

```bash
systemctl --user stop anistock-server
cp data/game-before-rebuild-<时间>.db data/game.db
rm -f data/game.db-wal data/game.db-shm
systemctl --user start anistock-server
```

备份是停服状态下的完整副本，恢复后与执行前完全相同。确认新历史没有问题后，可以删除备份。
